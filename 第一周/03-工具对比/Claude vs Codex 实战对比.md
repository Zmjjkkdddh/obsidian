# Claude vs Codex 实战对比

> 同一任务分别用 Claude Code 和 Codex 完成，记录真实体验差异。

---

## 测试任务

**选题**：写一个 Python 脚本，扫描 Obsidian 知识库所有 Markdown 文件，统计字数、Wiki 链接、标签、标题层级、代码块，生成分析报告并标注孤立页面。

**选择理由**：
- 不简单（需要正则解析、文件遍历、报告生成）
- 不过难（一个文件，~150 行）
- 有明确的可验证输出
- 贴近实际工作场景

---

## Round 1：Claude Code（本会话）

### 给它看什么？

直接告诉它任务描述，没有给任何示例或规范。Claude 自己设计了参数接口、JSON 输出、孤立页面检测。

### 实际发生的过程

| 步骤 | 行为 |
|------|------|
| 1. 理解需求 | 自动拆解为：文件扫描 → Markdown 解析 → 统计 → 报告 |
| 2. 考虑边界 | 中英文混统计、编码错误处理、隐藏目录跳过 |
| 3. 意外惊喜 | 自动加了 `--json` / `--sort` 参数、孤立页面检测 |
| 4. 写完后 | 主动运行测试（虽然 Python 没装，但尝试了） |

### 输出产物

`kb_analyzer.py`，约 160 行，结构：

```
参数解析 (argparse)
  → 扫描目录 (os.walk, 跳过 .hidden)
    → 解析文件 (YAML frontmatter, 中英文统计, 正则)
      → 生成报告 (text/json, 排序, 孤立页面检测)
```

### 意外设计决策

- Wiki 链接去重后列在报告中，方便检查
- `--sort words` 按字数排，快速找到最"厚"的页面
- 中文按字符数、英文按单词数分开统计后合并
- 自动跳过 `index` 和 `日报模板` 这类元页面

## Round 2：Codex（你来完成）

### 复制这段 Prompt 喂给 Codex

```
写一个 Python 脚本，扫描 Obsidian 知识库目录下的所有 .md 文件，
统计每个文件的：
- 中文字数和英文单词数
- Wiki 链接数量（[[...]] 格式）
- 标题数量和最大深度（H1-H6）
- 标签数量和去重后的标签列表
- 代码块数量
- YAML frontmatter 中的字段

然后生成一个格式化的汇总报告，按字数从多到少排序。
额外功能：检测孤立页面（没有被任何其他页面通过 Wiki 链接引用的页面）。
支持 --json 参数输出 JSON 格式。
```

### 记录这些

| 观察维度 | Claude | Codex |
|----------|--------|-------|
| 一次成功？ | 需要调试？（记录轮次） | |
| 代码风格 | 面向对象？函数式？注释量？ | |
| 边界处理 | 有没有考虑编码错误、空文件、嵌套目录？ | |
| 额外想法 | 有什么你没想到但它做了的？ | |
| 输出长度 | 多少行代码？ | |
| 对话轮次 | 几轮对话搞定？ | |
| 整体感觉 | 像跟谁合作？（资深工程师/初级助手/…） | |

## 初步观察（Claude 侧）

Claude Code 的行为模式：
- **主动拆解任务**，不需要我告诉它先做什么后做什么
- **一口气写完**，没有"先写框架再补充"的分步
- **加了参数设计**（argparse），考虑到了复用性
- **写完立刻想跑**——会主动验证
- **中英文统计分开做**——理解中文场景的特殊需求
- **孤立页面检测**——这个我没要求，它自己加的

> ⚠️ 局限：写代码风格偏"函数式脚本"，没有类封装。如果需求膨胀到 500+ 行，可能需要重构。
