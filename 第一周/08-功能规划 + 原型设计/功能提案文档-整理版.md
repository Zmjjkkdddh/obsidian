# 功能提案文档

> 基于产品规划书和 1 期 MVP 现状，对 8 个候选功能进行五维评估。

---

## 一、背景与评估框架

### 1.1 产品分期逻辑

产品以服务用户群的优先顺序为驱动，而非单纯按技术难度排序：

| 分期 | 目标用户群 | 核心目标 |
|------|-----------|---------|
| 1 期 | 公司内部运维/运营人员 | 跑通知识底座，验证知识库 + 文档助手的核心能力 |
| 2 期 | 业务部门内部员工（采购/电商/行政/财务/数据分析） | 打通自助问数与流程自动化，覆盖多系统协同场景 |
| 3 期 | 外部 B 端客户（标准包交付 + 少数私有化） | 将已验证能力标准化打包，形成可交付的产品包 |

### 1.2 评估维度说明

每个候选功能从以下五个维度进行评估：

| 评估维度 | 说明 |
|---------|------|
| 用户价值 | 解决的是不是真实痛点？影响面多大？ |
| 技术可行性 | 基于 Open WebUI + 自研服务层能不能实现？难度如何？ |
| 商业价值 | 对商业化有没有帮助？客户愿不愿意为此付费？ |
| 与 1 期协调性 | 和 1 期功能是否冲突？是否依赖 1 期未完成的功能？ |
| 优先级 | 2 期（近期必做）/ 3 期（远期规划） |

## 二、2 期候选功能 —— 服务用户群 B，打通数据与流程

---

### F1 · 自助 Agent 构建器

**功能名称**：自助 Agent 构建器（Self-service Agent Builder）

**解决什么问题**：
业务人员的日常重复工作（如每周汇总报价、对比数据、生成报表、发邮件）依赖手工操作或多个系统间切换，效率低且容易出错。传统自动化需要开发排期写脚本，业务人员无法自助完成。该功能让不懂代码的业务人员用自然语言描述需求，系统自动拆解并编排为可定期执行的 Agent 任务流。

**目标用户**：用户群 B（采购、行政、财务、电商运营等业务人员）

**功能描述**：
业务人员通过自然语言描述日常重复工作需求（如每周一自动汇总上周所有供应商报价，对比最低价，发邮件给经理），系统 AI 自动解析意图，提取触发条件、数据来源、处理逻辑和输出目标，拆解为可执行的任务步骤（定时触发 -> 查数据库 -> LLM 比价 -> 生成表格 -> 企微推送），以可视化工作流草稿展示给用户确认。用户可调整触发条件和步骤，测试运行后发布执行。每个 Agent 按定时/触发条件自动运行，每次执行记录日志，异常时自动暂停并通知用户。

| 评估维度 | 评估结论 |
|---------|---------|
| 用户价值 | 极高。业务部门大量重复性工作可被自动化，直接影响日常工作效率。影响面覆盖采购、行政、财务等多个职能部门 |
| 技术可行性 | 中等偏高。需要工作流编排引擎作为底层支撑（2 期已规划），在此基础上叠加 LLM 意图解析和步骤拆解。编排引擎是核心难点，Agent 层的自然语言到结构化任务流映射需要多轮迭代优化 |
| 商业价值 | 极高。是企业付费的核心驱动力之一，用 AI 替代重复人工操作，ROI 可量化。中等规模企业对此类自动化能力付费意愿强 |
| 与 1 期协调性 | 不冲突。依赖 2 期同步建设的工作流编排引擎，1 期已完成的 MCP 适配层和对话界面可直接复用 |
| 优先级 | 2 期 P0（必做） |

**实现难度评估**：较高

核心难点：工作流编排引擎的抽象设计、自然语言到结构化任务流的准确映射、多步骤任务的异常处理和回滚

**建议**：先支持 3-5 个预设场景模板（如采购比价、日报汇总），再逐步开放自由编排

---

### F2 · 多模型切换面板

**功能名称**：多模型切换面板（Multi-Model Switch Panel）

**解决什么问题**：
当前 1 期仅支持有限模型（Claude + DeepSeek），用户无法根据任务复杂度选择不同成本/能力的模型。所有请求跑同一个模型导致简单任务浪费 Token 成本，复杂任务又受限于模型能力天花板。同时，外部客户不希望被绑定在单一模型供应商上。

**目标用户**：用户群 A、B、C 全覆盖，但 2 期重点服务 B 端成本敏感场景

**功能描述**：
管理员后台接入多个 LLM 后端（混元 / DeepSeek / Claude / 通义千问 / 本地模型等），配置模型名、价格和能力标签。用户在对话界面通过下拉菜单自由切换模型，同时支持自动路由规则：按成本优先/质量优先/指定模型三档配置。系统按模型+用户+组织维度统计用量，为计费和成本分析提供数据基础。

| 评估维度 | 评估结论 |
|---------|---------|
| 用户价值 | 极高。直接降低使用成本（简单任务用便宜模型），同时保证复杂场景质量（强模型兜底）。对用户群 B 的数仓问数场景尤为关键 |
| 技术可行性 | 高。Open WebUI 已具备多模型切换能力，自研服务层只需在 MCP 适配层之上加模型路由层。1 期已完成的供应商接入体系可平滑扩展 |
| 商业价值 | 极高。多模型支持是向外部客户证明不被供应商锁定的关键卖点。支持客户使用自有模型供应商可降低其采购顾虑 |
| 与 1 期协调性 | 不冲突。1 期已支持 Claude + DeepSeek 双模型，2 期在此基础上扩展供应商数量和路由规则即可 |
| 优先级 | 2 期 P0（必做） |

**实现难度评估**：中等

模型路由层需要统一不同供应商的 API 协议差异

自动路由规则的设计需要平衡成本、能力、延迟三个维度

**建议**：首批接入混元 Turbo、通义千问 Qwen-Max、GPT-4o-mini

### F3 · 对话质量反馈环

**功能名称**：对话质量反馈环（Conversation Quality Feedback Loop）

**解决什么问题**：
1 期没有反馈机制，无法知道 AI 回答好不好、哪些知识库内容需要修正。知识库管理员只能凭人工抽查来发现问题，效率低且滞后。对于向客户证明 AI 在持续变好也缺乏数据支撑。

**目标用户**：全体用户（反馈端）+ 知识库管理员（处理端）

**功能描述**：
每条 AI 回复旁加点赞/点踩按钮。用户点踩时弹出分类标签选择（答非所问/数据错误/格式不对/内容太简略/其他）。低分回答自动进入管理员审核队列，按影响人数和频次排序。管理员可修正知识库内容、调整 Prompt 或标记为用户理解偏差。每周自动生成质量周报（好评率趋势/高频踩因/改正数量），形成闭环优化。

| 评估维度 | 评估结论 |
|---------|---------|
| 用户价值 | 较高。为用户提供表达不满的出口，为管理员提供优化方向。长期看能持续提升回答质量 |
| 技术可行性 | 高。点赞/点踩是成熟的产品模式，分类标签和审核队列均为标准 CRUD 操作。唯一需要设计的是反馈如何驱动知识库权重的自动调整 |
| 商业价值 | 较高。质量周报可纳入客户月度报告，向客户证明 AI 在使用中不断进化，增强续费信心 |
| 与 1 期协调性 | 不冲突。纯增量功能，不影响 1 期任何现有流程。但审核队列需关联知识库管理系统 |
| 优先级 | 2 期 P1（建议做） |

**实现难度评估**：较低

反馈收集和审核队列技术简单

反馈到知识库权重调整的自动化策略需要谨慎设计，避免误调

建议：先从 👍👎 基础反馈做起，跑通闭环后再叠加权重自动调整

---

### F4 · 协作工作空间

**功能名称**：协作工作空间（Collaboration Workspace）

**解决什么问题**：
当前知识库和对话记录均为个人隔离，团队无法共享经验。某人补充的案例、踩过的坑其他人看不到，经验随人员流失。部门管理员无法了解团队整体使用情况和知识覆盖盲区。

**目标用户**：用户群 B（多职能部门团队协作场景）

**功能描述**：
支持创建团队空间，成员共享知识库、对话历史、Prompt 模板。成员可在对话中 @其他人分享当前对话。管理员可按成员角色（管理员/编辑/只读）分配权限。提供团队面板：用量排名、热门问题 TOP 10、知识库覆盖盲区（本月最常问但知识库没有的 TOP 5）、团队反馈统计。

| 评估维度 | 评估结论 |
|---------|---------|
| 用户价值 | 较高。运维、客服等依赖经验共享的团队受益最大。对个人独立工作场景价值有限 |
| 技术可行性 | 中等偏高。核心挑战在于：数据权限模型的重新设计（从个人隔离扩展到团队共享+组织隔离）、对话记录的实时共享机制、知识盲区检测的统计计算 |
| 商业价值 | 中等。团队协作是 B 端产品的标配能力，客户期待但不太愿意单独为此付费。更多是提升产品完整性和粘性 |
| 与 1 期协调性 | 需注意。1 期的数据隔离模型是按组织严格隔离，2 期需要在组织内增加团队层级。需谨慎设计权限模型，避免破坏 1 期的安全隔离承诺 |
| 优先级 | 2 期 P1（建议做） |

**实现难度评估**：中等偏上

权限模型的层级扩展（组织->团队->个人）是架构层面的改动

知识盲区检测需要统计对话中的未命中检索记录

建议：先做共享知识库（技术简单、价值直接），团队面板功能放二期迭代

### F5 · 智能通知与主动推送

**功能名称**：智能通知与主动推送（Smart Notification and Push）

**解决什么问题**：
当前产品是被动问答模式——用户不主动问，AI 就不给答案。运维告警、审批到达、数据异常等场景需要 AI 主动告知用户该处理这个了，而非等用户发现问题再来查询。

**目标用户**：用户群 A（运维监控场景）+ 用户群 B（审批流程、数据异常预警）

**功能描述**：
接入系统告警、审批节点、定时规则、数据异常等触发源。触发后 AI 自动分析内容（提取关键信息->匹配知识库->生成建议），生成通知（标题+摘要+建议操作+一键跳转链接），按用户偏好推送到企微/钉钉/邮件。未处理超时自动升级通知（推给上级）。通知历史可检索，每周汇总到运维周报。

| 评估维度 | 评估结论 |
|---------|---------|
| 用户价值 | 极高。从被动到主动的模式升级，运维场景的告警智能分析是刚需痛点。审批流转的自动通知也有明显效率提升 |
| 技术可行性 | 中等。核心难度在于：外部系统告警的接入适配（不同系统格式各异）、通知渠道的对接（企微/钉钉/邮件）、升级规则的灵活配置 |
| 商业价值 | 较高。主动服务能力是产品差异化的关键卖点，运维告警智能分析可独立包装为增值模块 |
| 与 1 期协调性 | 不冲突。纯增量功能，依赖 1 期的 MCP 适配层对接外部告警系统，依赖 1 期的知识库做告警内容分析 |
| 优先级 | 2 期 P1（建议做） |

**实现难度评估**：中等

通知规则引擎的设计需要灵活可配置

多渠道推送需要统一的消息中间层

**建议**：首期仅对接企微和邮件两个渠道，后续扩展钉钉

## 三、3 期候选功能 —— 服务用户群 C，能力标准化交付

---

### F6 · 对话能力增强

**功能名称**：对话能力增强（Conversation Enhancement）

**解决什么问题**：
1 期对话体验存在三个明显短板：(1) AI 回答缺乏来源标注，用户无法判断可信度；(2) 生成过程中用户无法中断，必须等全部说完才能纠正；(3) 无法从某条消息分叉探索不同方案，对比效率低。

**目标用户**：全体用户（尤其是运维、采购等依赖高质量输出的场景）

**功能描述**：

- **回答引用溯源（P0）**：每段回答标注知识库来源段落，用户可悬停预览原文、点击跳转知识库原文。无来源的 AI 自由推理内容标注为 AI 推理生成
- **流式输出中断（P1）**：用户可随时按停止键打断生成，保留已生成部分，修改后重新生成
- **对话分支（P2）**：从某条消息一键分叉，让 AI 从多个角度（如价格/交期/信用/售后）各生成一个方案，用户并排对比选择

| 评估维度 | 评估结论 |
|---------|---------|
| 用户价值 | 极高。引用溯源直接回应了企业用户 AI 回答是否可信的核心疑虑；流式中断是交互体验的基础能力；对话分支是差异化亮点 |
| 技术可行性 | 引用溯源和流式中断技术难度中等，对话分支较高。引用溯源只需在 RAG 检索结果中保留原文引用并前端渲染。流式中断是标准 SSE 能力。对话分支需要对话树数据结构改造 |
| 商业价值 | 较高。引用溯源是向外部客户交付时的必备能力——客户需要可解释的 AI。对话分支适合向 C 端客户展示产品差异化 |
| 与 1 期协调性 | 不冲突。均为对话模块的增量增强。对话分支需要改造消息数据结构（从线性列表到对话树），影响面较大 |
| 优先级 | 3 期 P1（引用溯源可提前至 2 期作为 P0） |

**实现难度评估**：

| 子功能 | 难度 | 说明 |
|--------|------|------|
| 引用溯源 | 较低 | RAG 链路已有来源信息，主要是前端渲染 |
| 流式中断 | 较低 | SSE 标准能力 |
| 对话分支 | 较高 | 需要对话树数据模型 + 分叉 UI 交互 |

---

### F7 · 知识图谱引擎

**功能名称**：知识图谱引擎（Knowledge Graph Engine）

**解决什么问题**：
1 期知识库基于关键词 + 向量检索，只能做语义相似的匹配。当用户问"数据库 C 挂了影响哪些服务？"这类需要推理实体间关系的问题时，向量检索无法给出准确答案。运维、架构等场景需要理解组件间的依赖关系。

**目标用户**：用户群 A（运维架构师）、用户群 C（差异化能力交付）

**功能描述**：
在向量检索之上构建实体关系图——从知识库文档中自动提取实体（服务器名/IP、服务名、数据库名、人员名）和关系（运行于、依赖、调用、备份到、负责人），形成可视化交互图谱。用户可点击节点展开详情。当用户问影响范围类问题时，系统自动触发图谱推理，给出完整的影响链路和建议处理顺序。

| 评估维度 | 评估结论 |
|---------|---------|
| 用户价值 | 较高（运维场景）、一般（其他场景）。运维和架构场景是强需求，但对采购、行政等场景价值有限。影响面较窄 |
| 技术可行性 | 较低到中等。实体识别和关系抽取的准确率是核心挑战——NLP 模型在处理非结构化运维文档时容易出现误提取。图谱构建需要人工审核环节，无法完全自动化 |
| 商业价值 | 较高。知识图谱是明显的技术差异化能力，适合向大型客户展示产品技术深度。但建设和维护成本高，ROI 需要评估 |
| 与 1 期协调性 | 不冲突。依赖 1 期的知识库作为实体抽取的数据源，叠加图谱层增强检索能力。不影响现有向量检索 |
| 优先级 | 3 期 P1（远期规划） |

**实现难度评估**：

| 子功能 | 难度 | 说明 |
|--------|------|------|
| 实体抽取 | 高 | NLP 难点，运维文档格式多样、术语不规范 |
| 关系建模 | 较高 | 关系类型定义 + 跨文档关系拼接 |
| 图谱可视化 | 中等 | 节点/边的动态布局 |
| 图谱增强问答 | 较高 | 图谱推理引擎 + 与向量检索的融合策略 |
| 增量更新 | 较高 | 文档变更后自动同步，需避免全量重建 |

**建议**：先在 1-2 个运维场景做 PoC 验证准确率，再决定是否全量投入

### F8 · 用量分析

**功能名称**：用量分析（Usage Analytics）

**解决什么问题**：
3 期面向外部客户交付时，客户 IT 负责人需要向老板证明这笔钱花得值——各部门用了多少次、省了多少人工、哪个部门用得最好。没有数据支撑的续费决策是脆弱的。同时，管理员需要成本预警机制防止 Token 费用失控。

**目标用户**：外部客户的 IT 负责人/管理员（用户群 C）

**功能描述**：
每次对话自动记录用户、部门、模型、Token 消耗、耗时、反馈等数据。提供实时仪表盘：今日用量/本月趋势/热门问题 TOP 10/部门排名。每月自动生成 PDF 月度报告（摘要+趋势+ROI 核算+建议）。支持预算/部门/Token 上限的预警和熔断机制（达到 80% 预警，100% 熔断并通知管理员）。

| 评估维度 | 评估结论 |
|---------|---------|
| 用户价值 | 极高（对客户管理员）、一般（对普通用户）。客户 IT 负责人是续费决策的关键角色，ROI 报告直接影响续费 |
| 技术可行性 | 高。本质是数据采集+聚合统计+可视化，技术栈成熟。1 期 Token 计量已有基础，只需扩展采集维度和输出形式 |
| 商业价值 | 极高。是续费驱动的核心工具——让客户看得见价值。也可作为独立分析模块单独计费 |
| 与 1 期协调性 | 不冲突。1 期的 Token 计量计费已打下数据采集基础。2 期多模型切换面板会产生更丰富的用量数据 |
| 优先级 | 3 期 P1（建议 2 期预埋数据采集，3 期建设分析能力） |

**实现难度评估**：

| 子功能 | 难度 | 说明 |
|--------|------|------|
| 数据采集 | 较低 | 1 期 Token 计量已有基础，扩展用户/部门/模型维度 |
| 聚合统计 | 较低 | 标准 OLAP 聚合，按时/天/月汇总 |
| 实时仪表盘 | 中等 | 图表组件 + 实时刷新 |
| 月度报告生成 | 中等 | PDF 模板引擎 + 自动推送 |
| 预算预警/熔断 | 较低 | 规则引擎 + 阈值通知 |

**建议**：2 期就预埋完整的用量数据采集，避免后期补数据

| 功能编号 | 功能名称 | 用户价值 | 技术难度 | 商业价值 | 分期建议 | 综合优先级 |

### 建议的开发顺序

**2 期第一批（P0，必须交付）：**

F2 多模型切换面板（技术难度低、用户价值高）和 F1 自助 Agent 构建器（用户价值极高、但需先建编排引擎）

**2 期第二批（P1，建议交付）：**

F3 对话质量反馈环（闭环优化的基础设施）、F5 智能通知与推送（主动服务的关键能力）、F4 协作工作空间（架构影响较大，建议靠后）

**3 期（远期规划）：**

F8 用量分析（2 期预埋采集，3 期建设）、F6 对话能力增强（引用溯源码可提前至 2 期）、F7 知识图谱引擎（建议先 PoC 再全量）
