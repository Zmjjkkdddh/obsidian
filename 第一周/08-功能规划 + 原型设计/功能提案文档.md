# 功能提案文档


## 一、背景与评估框架

### 1.1 产品分期逻辑

产品推进以服务用户群的优先顺序为驱动，而非单纯按技术难度：

| 分期 | 目标用户群 | 核心目标 |
|------|-----------|---------|
| 1 期 | 内部运维/运营人员 | 跑通知识底座：知识库 + 文档助手 |
| 2 期 | 业务部门员工（采购/电商/行政/财务/数据分析） | 自助问数 + 流程自动化 + 多系统协同 |
| 3 期 | 外部 B 端客户（标准包 + 私有化） | 能力标准化打包，形成可交付产品 |

### 1.2 评估维度说明

| 评估维度 | 核心问题 |
|---------|---------|
| **用户价值** | 是不是真实痛点？影响面多大？ |
| **技术可行性** | 基于 Open WebUI + 自研服务层能否实现？难度如何？ |
| **商业价值** | 对商业化有没有帮助？客户愿意为此付费吗？ |
| **与 1 期协调性** | 和 1 期功能是否冲突？是否依赖 1 期未完成的能力？ |
| **优先级** | 2 期 P0（必做）/ 2 期 P1（建议做）/ 3 期 P1（远期规划） |

## 二、2 期候选功能 —— 服务用户群 B，打通数据与流程

---

### F1 · 自助 Agent 构建器

**功能名称**：自助 Agent 构建器（Self-service Agent Builder）

**解决什么问题**：
业务人员的大量日常重复工作——汇总报价、对比数据、生成报表、发邮件——依赖手工操作或多系统切换，效率低、易出错。传统自动化必须等开发排期写脚本，业务人员无法自助完成。

**目标用户**：用户群 B（采购、行政、财务、电商运营等业务人员）

**功能描述**：
用户用自然语言描述重复工作需求，系统自动解析意图并编排为可定期执行的 Agent 任务流。例如，采购员输入"每周一汇总上周所有供应商报价，对比最低价，发邮件给经理"，系统自动拆解为：定时触发 → 查数据库 → LLM 比价 → 生成表格 → 企微推送。用户可在可视化草稿中调整触发条件和步骤，测试后发布执行。每个 Agent 按计划自动运行，异常时暂停并通知用户，全程记录执行日志。

**子功能拆解**：

| 子功能 | 说明 | 优先级 |
|--------|------|--------|
| 意图解析引擎 | 自然语言 → 结构化任务描述的映射 | P0 |
| 工作流可视化编辑器 | 任务步骤展示 + 拖拽调整 | P0 |
| 任务执行引擎 | 定时/事件触发 + 步骤调度 + 异常回滚 | P0 |
| 执行日志与通知 | 每次执行记录 + 异常自动通知 | P1 |

**五维评估**：

| 评估维度 | 评估结论 |
|---------|---------|
| 用户价值 | 极高。直接影响多职能部门的日常效率，影响面覆盖采购、行政、财务等 |
| 技术可行性 | 中等偏高。底层依赖工作流编排引擎（2 期同步建设），上层 NL→结构化任务的映射需多轮迭代 |
| 商业价值 | 极高。AI 替代重复人工是量化 ROI 的核心场景，中等规模企业付费意愿强 |
| 与 1 期协调性 | 不冲突。依赖 2 期编排引擎；1 期的 MCP 适配层和对话界面可直接复用 |
| 优先级 | **2 期 P0（必做）** |

**实现难度**：较高。核心难点——编排引擎的抽象设计、自然语言到任务流的准确映射、多步骤的异常处理与回滚。

**建议**：先支持 3~5 个预设场景模板（采购比价、日报汇总），跑通后再开放自由编排。

### F2 · 多模型切换面板

**功能名称**：多模型切换面板（Multi-Model Switch Panel）

**解决什么问题**：
1 期仅支持有限模型，用户无法按任务复杂度选择不同成本/能力的模型。所有请求共用单一模型，简单任务浪费 Token，复杂任务又碰能力天花板。外部客户也不希望绑定单一供应商。

**目标用户**：用户群 A/B/C 全覆盖；2 期重点服务 B 端的成本敏感场景

**功能描述**：
管理员后台一键接入多个 LLM 后端（混元 / DeepSeek / Claude / 通义千问 / 本地模型），配置名称、价格和能力标签。用户在对话界面下拉切换模型，同时支持自动路由——按"成本优先/质量优先/指定模型"三档规则自动匹配。系统按模型→用户→组织维度统计用量，为计费和成本分析提供数据基础。

**子功能拆解**：

| 子功能 | 说明 | 优先级 |
|--------|------|--------|
| 模型后端管理 | 接入/配置/测试/下线各 LLM 供应商 | P0 |
| 用户切换面板 | 对话界面下拉切换 + 对话绑定模型 | P0 |
| 自动路由规则 | 成本优先/质量优先/指定模型三档 | P1 |
| 用量统计 | 按模型/用户/组织维度的 Token 消费追踪 | P1 |

**五维评估**：

| 评估维度 | 评估结论 |
|---------|---------|
| 用户价值 | 极高。直接降低使用成本，同时保证复杂场景质量。对 B 端的数仓问数场景尤为关键 |
| 技术可行性 | 高。Open WebUI 已具备多模型能力，自研层只需在 MCP 之上加模型路由。1 期供应商接入体系可平滑扩展 |
| 商业价值 | 极高。多模型支持是向客户证明"不锁定供应商"的关键卖点 |
| 与 1 期协调性 | 不冲突。1 期已支持 Claude + DeepSeek，2 期扩展供应商数量和路由规则 |
| 优先级 | **2 期 P0（必做）** |

**实现难度**：中等。核心难点——统一不同供应商 API 协议差异；路由规则需平衡成本、能力、延迟三维度。

**建议**：首批接入混元 Turbo、通义千问 Qwen-Max、GPT-4o-mini（覆盖低价/中文/多模态三个维度）。

### F3 · 对话质量反馈环

**功能名称**：对话质量反馈环（Conversation Quality Feedback Loop）

**解决什么问题**：
1 期没有反馈机制——不知道 AI 回答好不好、知识库哪里需要修正。管理员只能人工抽查发现问题，效率低且滞后。缺乏向客户展示"AI 正在变好"的数据支撑。

**目标用户**：全体用户（反馈端）+ 知识库管理员（处理端）

**功能描述**：
每条 AI 回复旁加 👍👎 按钮。👎 时弹出分类标签（答非所问/数据错误/格式不对/内容太简略/其他）。低分回答自动进入审核队列，按影响人数排序。管理员可修正知识库、调整 Prompt，或标记为"用户理解偏差"。每周自动生成质量周报（好评率趋势/高频踩因/改正数量），形成闭环。

**子功能拆解**：

| 子功能 | 说明 | 优先级 |
|--------|------|--------|
| 👍👎 反馈收集 | 点赞/点踩 + 分类标签 | P0 |
| 审核队列 | 低分回答自动入队 + 排序 + 处理 | P0 |
| 知识库关联修正 | 从反馈直接跳转→修正知识库片段 | P1 |
| 质量周报 | 自动生成好评率/踩因/改正数量报告 | P2 |

**五维评估**：

| 评估维度 | 评估结论 |
|---------|---------|
| 用户价值 | 较高。给用户表达的出口，给管理员优化的方向，长期持续提升回答质量 |
| 技术可行性 | 高。点赞/点踩是成熟模式，分类标签和审核队列均为标准 CRUD |
| 商业价值 | 较高。质量周报可纳入客户月度报告，证明 AI 持续进化，增强续费信心 |
| 与 1 期协调性 | 不冲突。纯增量功能，审核队列需关联知识库管理系统 |
| 优先级 | **2 期 P1（建议做）** |

**实现难度**：较低。技术简单，但反馈→知识库权重自动调整的策略需谨慎设计，避免误调。

### F4 · 协作工作空间

**功能名称**：协作工作空间（Collaboration Workspace）

**解决什么问题**：
当前知识库和对话记录均为个人隔离，团队无法共享经验。某人补充的案例、踩过的坑其他人看不到，随人员流失而丢失。部门管理员无法了解团队整体使用情况和知识覆盖盲区。

**目标用户**：用户群 B（多职能团队协作场景）

**功能描述**：
创建团队空间，成员共享知识库、对话历史、Prompt 模板。对话中可 @成员分享当前内容。管理员按角色（管理员/编辑/只读）分配权限。提供团队面板：用量排名、热门问题 TOP 10、知识库覆盖盲区（本月最常问但知识库没有的 TOP 5）、团队反馈统计。

**子功能拆解**：

| 子功能 | 说明 | 优先级 |
|--------|------|--------|
| 团队创建与成员管理 | 创建空间 + 邀请 + 角色分配 | P0 |
| 共享知识库 | 团队级知识库可见性配置 | P0 |
| 共享对话与模板 | 对话分享 + 团队专属模板库 | P1 |
| 团队面板 | 用量/热门问题/盲区/反馈统计 | P1 |

**五维评估**：

| 评估维度 | 评估结论 |
|---------|---------|
| 用户价值 | 较高。运维、客服等依赖经验共享的团队受益最大；独立工作场景价值有限 |
| 技术可行性 | 中等偏高。核心挑战：权限模型从个人→团队+组织的层级扩展、对话实时共享、盲区检测的统计计算 |
| 商业价值 | 中等。B 端标配能力，客户期待但不太愿单独付费，更多是提升产品完整性和粘性 |
| 与 1 期协调性 | ⚠️ 需注意。1 期按组织严格隔离数据，2 期在组织内增加团队层级，需谨慎设计权限模型 |
| 优先级 | **2 期 P1（建议做）** |

**实现难度**：中等偏上。权限模型层级扩展是架构级改动；知识盲区检测需统计对话中的未命中检索记录。

### F5 · 智能通知与主动推送

**功能名称**：智能通知与主动推送（Smart Notification & Push）

**解决什么问题**：
当前产品是被动问答模式——用户不问，AI 就不说。运维告警、审批到达、数据异常等场景需要 AI 主动告知用户"该处理了"，而非等用户发现后再来查询。

**目标用户**：用户群 A（运维监控）+ 用户群 B（审批流程、数据异常预警）

**功能描述**：
接入系统告警、审批节点、定时规则、数据异常阈值等触发源。触发后 AI 自动分析内容（提取关键信息→匹配知识库→生成处理建议），生成通知（标题+摘要+建议操作+一键跳转），按用户偏好推送到企微/钉钉/邮件。未处理超时自动升级推给上级。通知历史可检索，每周汇总到运维周报。

**子功能拆解**：

| 子功能 | 说明 | 优先级 |
|--------|------|--------|
| 触发源接入 | 系统告警/审批节点/定时规则/异常阈值的对接 | P0 |
| AI 分析与生成 | 提取信息→匹配知识库→生成摘要+建议 | P0 |
| 多渠道推送 | 企微/钉钉/邮件统一消息中间层 | P0 |
| 升级规则引擎 | 未处理超时→升级推送上级 | P1 |

**五维评估**：

| 评估维度 | 评估结论 |
|---------|---------|
| 用户价值 | 极高。从被动到主动的模式升级。运维告警智能分析是刚需；审批流转通知有明显效率提升 |
| 技术可行性 | 中等。难点：外部系统告警格式各异需逐系统适配、通知渠道对接、升级规则灵活配置 |
| 商业价值 | 较高。主动服务是差异化关键卖点，运维告警分析可独立包装为增值模块 |
| 与 1 期协调性 | 不冲突。依赖 1 期的 MCP 适配层对接外部系统，依赖知识库做告警内容分析 |
| 优先级 | **2 期 P1（建议做）** |

**实现难度**：中等。通知规则引擎需灵活可配置；多渠道推送需统一消息中间层。

**建议**：首期仅对接企微和邮件两个渠道，后续扩展钉钉。

## 三、3 期候选功能 —— 服务用户群 C，对外打包交付

---

### F6 · 对话能力增强

**功能名称**：对话能力增强（Conversation Enhancement）

**解决什么问题**：
1 期对话体验有三个明显短板：① AI 回答无来源标注，用户无法判断可信度；② 生成中无法中断，必须等全部输出才能纠正；③ 无法从某条消息分叉探索多个方案，只能线性对话。

**目标用户**：全体用户；运维、采购等依赖高质量输出的场景受益最大

**功能描述**：

| 子功能 | 说明 | 优先级 |
|--------|------|--------|
| 回答引用溯源 | 每段回答标注知识库来源，悬停预览原文，点击跳转。无来源内容标注"AI 推理生成" | P0 |
| 流式输出中断 | 用户随时按停止键打断生成，保留已生成部分，修正后重试 | P1 |
| 对话分支 | 从某条消息一键分叉，让 AI 从多个角度（价格/交期/信用）各生成方案，并排对比 | P2 |

**五维评估**：

| 评估维度 | 评估结论 |
|---------|---------|
| 用户价值 | 极高。引用溯源回应了企业用户对 AI 可信度的核心疑虑；流式中断是基础交互能力；对话分支是差异化亮点 |
| 技术可行性 | 引用溯源和流式中断较低（分别在 RAG 链路上加渲染、SSE 标准能力）。对话分支较高（需要对话树数据模型改造） |
| 商业价值 | 较高。引用溯源是交付外部客户的必备能力；对话分支适合向客户展示差异化 |
| 与 1 期协调性 | 不冲突。对话分支需改造消息数据结构（线性→对话树），影响面较大 |
| 优先级 | **3 期 P1**（引用溯源可提前至 2 期作为 P0） |

**实现难度**：

| 子功能 | 难度 | 说明 |
|--------|------|------|
| 引用溯源 | 较低 | RAG 链路已有来源信息，主要是前端渲染 + 来源失效处理 |
| 流式中断 | 较低 | SSE 标准能力，前端加停止按钮 |
| 对话分支 | 较高 | 对话树数据模型 + 分叉 UI + 多分支并行生成管理 |

**建议**：引用溯源提前至 2 期（开发成本低、用户感知强）；对话分支 3 期独立迭代。

### F7 · 知识图谱引擎

**功能名称**：知识图谱引擎（Knowledge Graph Engine）

**解决什么问题**：
1 期知识库基于关键词+向量检索，只能做语义相似的片段匹配。当用户问"数据库 C 挂了影响哪些服务？"这类需要**推理实体间关系**的问题时，向量检索无法给出准确答案。运维和架构场景需要理解组件间的依赖关系。

**目标用户**：用户群 A（运维架构师）+ 用户群 C（差异化能力交付）

**功能描述**：
在向量检索之上叠加实体关系图——从知识库文档中自动抽取实体（服务器/IP、服务名、数据库名、人员名）和关系（运行于、依赖、调用、备份到、负责人），形成可视化交互图谱。用户点击节点展开详情。问影响范围类问题时自动触发图谱推理，给出完整影响链路和处理顺序。

**子功能拆解**：

| 子功能 | 说明 | 优先级 |
|--------|------|--------|
| 实体抽取 | NLP 自动提取文档中的实体名称和类型 | P0 |
| 关系建模 | 识别实体间关系 + 跨文档关系拼接 | P0 |
| 图谱可视化 | 可交互的节点-边图谱渲染 | P1 |
| 图谱增强问答 | 图谱推理引擎 + 与向量检索的融合策略 | P1 |
| 增量更新 | 文档变更后图谱自动同步 | P2 |

**五维评估**：

| 评估维度 | 评估结论 |
|---------|---------|
| 用户价值 | 较高（运维场景强需求）、一般（其他场景）。影响面较窄 |
| 技术可行性 | 较低到中等。实体抽取准确率是核心挑战——非结构化运维文档格式多样、术语不规范；图谱构建需人工审核 |
| 商业价值 | 较高。明显的技术差异化能力，适合向大客户展示技术深度。但建设和维护成本高 |
| 与 1 期协调性 | 不冲突。依赖知识库作为数据源，叠加图谱层增强检索，不影响现有向量检索 |
| 优先级 | **3 期 P1（远期规划）** |

**实现难度**：

| 子功能 | 难度 | 说明 |
|--------|------|------|
| 实体抽取 | 高 | NLP 难点，运维文档术语不规范 |
| 关系建模 | 较高 | 关系类型定义 + 跨文档拼接 |
| 图谱可视化 | 中等 | 节点/边动态布局 |
| 图谱增强问答 | 较高 | 图谱推理 + 向量检索融合 |
| 增量更新 | 较高 | 变更后自动同步，需避免全量重建 |

**建议**：先在 1~2 个运维场景做 PoC 验证实体抽取准确率（目标 >70%），再决定是否全量投入。可视化先做简化版（静态力导向图），3 期迭代交互版。

### F8 · 用量分析

**功能名称**：用量分析（Usage Analytics）

**解决什么问题**：
3 期面向外部客户交付时，客户 IT 负责人需要数据向老板证明 ROI——各部门用了多少次、省了多少人工、哪个部门用得最好。没有数据支撑的续费决策是脆弱的。同时管理员需要成本预警防止 Token 费用失控。

**目标用户**：外部客户的 IT 负责人/管理员（用户群 C）

**功能描述**：
每次对话自动记录用户、部门、模型、Token、耗时、反馈。提供实时仪表盘：今日用量/本月趋势/热门问题 TOP 10/部门排名。每月 1 号自动生成 PDF 月度报告（摘要+趋势+ROI 核算+优化建议）。支持预算/部门/Token 上限的预警和熔断（80% 预警，100% 熔断并通知管理员）。

**子功能拆解**：

| 子功能 | 说明 | 优先级 |
|--------|------|--------|
| 用量数据采集 | 每次对话的埋点记录（用户/部门/模型/Token/耗时/反馈） | P0 |
| 实时仪表盘 | 图表组件 + 多维度筛选 + 实时刷新 | P0 |
| 月度报告自动生成 | PDF 模板引擎 + 自动发送邮件/企微 | P1 |
| 预算预警与熔断 | 阈值规则 + 达标通知/自动限流 | P1 |

**五维评估**：

| 评估维度 | 评估结论 |
|---------|---------|
| 用户价值 | 极高（对客户管理员）、一般（对普通用户）。IT 负责人是续费决策的关键角色 |
| 技术可行性 | 高。数据采集+聚合统计+可视化，技术栈成熟。1 期 Token 计量已有基础 |
| 商业价值 | 极高。续费驱动的核心工具——让客户看得见价值。可独立包装为增值分析模块 |
| 与 1 期协调性 | 不冲突。1 期 Token 计量已打下基础；2 期多模型切换会产生更丰富的用量数据 |
| 优先级 | **3 期 P1**（建议 2 期预埋数据采集，3 期建设分析能力） |

**实现难度**：

| 子功能 | 难度 | 说明 |
|--------|------|------|
| 数据采集 | 较低 | 扩展 1 期 Token 埋点，增加用户/部门/模型维度 |
| 聚合统计 | 较低 | 标准 OLAP 按时/天/月汇总 |
| 实时仪表盘 | 中等 | 图表组件 + 实时刷新 |
| 月度报告生成 | 中等 | PDF 模板引擎 + 自动推送 |
| 预算预警/熔断 | 较低 | 规则引擎 + 阈值通知 |

**建议**：2 期预埋完整的数据采集（一劳永逸）；3 期建设仪表盘和报告。月度报告格式先和种子客户共创，避免自嗨。

## 四、优先级矩阵总览

| # | 功能名称 | 用户价值 | 技术难度 | 商业价值 | 分期 | 优先级 |

### 建议开发顺序

**2 期第一批（P0）**：F2 多模型切换（难度低、价值高）→ F1 自助 Agent（价值极高，但需先建编排引擎）

**2 期第二批（P1）**：F3 质量反馈环（闭环优化的基础设施）→ F5 智能通知（主动服务关键能力）→ F4 协作工作空间（架构影响大，靠后）

**3 期**：F8 用量分析（2 期预埋采集）→ F6 对话增强（引用溯源可提前至 2 期）→ F7 知识图谱（先 PoC 再全量）
